# Cloudflare DNS для официального Nginx Proxy Manager

Отдельный модуль на Node.js 24 без npm-зависимостей. Подключается к официальному NPM в Docker и к обычной установке на Linux: проксирует административный порт, добавляет JavaScript/CSS в HTML и выполняет фоновую синхронизацию через Cloudflare API. Код NPM не патчится. Это внешний адаптер, а не встроенная система плагинов NPM.

Для Docker используется дополнительный контейнер. Для Linux без контейнеров предусмотрен [установщик systemd/OpenRC](docs/linux-install.md): он переносит только административный nginx listener на loopback-порт, сохраняя сайты на 80/443.

## Поведение

В таблице Proxy Hosts появляется столбец **CF DNS** с тремя иконками. Настройки расположены в **Settings → Cloudflare DNS**, отдельной вкладке под **Default Site**. Подсказки доступны при наведении и фокусе; Escape закрывает подсказку. Включённое состояние отмечено цветом и `aria-pressed`.

- **Sync**: при ON модуль создаёт недостающие A-записи и приводит их IP/Proxy к заданному состоянию. OFF сохраняет DNS-записи и прекращает их автоматическое изменение. Чтение состояния Cloudflare продолжается.
- **Proxy**: ON включает Cloudflare Proxy, OFF включает DNS only. При Sync OFF эта кнопка изменяет только `proxied`, не IP. Для создания отсутствующей записи сначала включите Sync.
- **Удалить**: после подтверждения выключает Sync и удаляет A-записи доменов хоста. Сам Proxy Host NPM остаётся. Если удаление частично не удалось, Sync остаётся OFF; кнопку можно нажать повторно.

Все действия применяются ко **всем доменам одного Proxy Host**, включая wildcard и IDN. Домены могут принадлежать разным доступным токену зонам. Запросы к нескольким доменам последовательные и не являются атомарной транзакцией Cloudflare: при частичном сбое уже выполненные операции сохраняются. Sync ON повторяет проверку в следующем цикле.

Worker работает без открытого браузера: первая проверка при запуске модуля, затем каждые 60 секунд. После отдельного перезапуска NPM проверка произойдёт в следующем цикле. Сеть и NPM могут быть ещё недоступны при старте; worker повторяет попытки. Сохранённые флаги и токен восстанавливаются из отдельного volume.

При первом успешном чтении базы **существующие** хосты получают Sync OFF. Новые обнаруженные хосты по умолчанию получают Sync ON и Proxy OFF; defaults изменяются в Settings. Изменение defaults не переключает существующие хосты. Удаление хоста или домена в NPM не удаляет старую DNS-запись автоматически. При выключении самого Proxy Host в NPM DNS продолжает синхронизироваться, если Sync ON.

## Установка на существующий NPM

Сначала получите исходники:

```sh
git clone https://github.com/MaksSt/npm-cloudflare-dns-module.git
cd npm-cloudflare-dns-module
```

1. Сохраните текущий Compose и резервную копию данных NPM. Сохраните пути к его существующим `/data` и `/etc/letsencrypt`.
2. Добавьте сервис из примера ниже в текущий Compose. `build.context` указывает на каталог этого проекта, `NPM_URL` — на имя вашего сервиса NPM. Оба сервиса должны быть в одной Docker-сети.
3. Уберите публикацию `81:81` у NPM и перенесите тот же внешний порт на модуль (`81:8080`). Публикация 80/443 и volumes NPM остаются как в текущей установке. Если админка уже опубликована на другом порту или адресе LAN, сохраните тот же внешний порт/адрес у модуля.
4. Примените конфигурацию: `docker compose up -d --build`. Откройте админку по прежнему адресу, войдите администратором и в **Settings → Cloudflare DNS** сохраните API Token.
5. Включите Sync для нужных существующих хостов. Дальнейшие новые хосты создадут записи автоматически согласно defaults.

```yaml
services:
  # Существующий сервис app с официальным образом NPM остаётся в этом Compose.
  cf-dns:
    build:
      context: /path/to/npm-cloudflare-dns-module
    restart: unless-stopped
    depends_on:
      - app
    ports:
      - "81:8080"
    environment:
      NPM_URL: http://app:81
      NPM_SQLITE_PATH: /npm-data/database.sqlite
      SYNC_INTERVAL_SECONDS: "60"
    volumes:
      - ./data:/npm-data:ro
      - cf-dns-data:/data

volumes:
  cf-dns-data:
```

`./data` должен быть **тем же существующим каталогом данных NPM**, относительно вашего Compose. При named volume подключите тот же volume второму сервису read-only. Монтируется весь каталог, чтобы были видны SQLite WAL/SHM. Пользователь `node` модуля должен иметь право читать базу и каталог; модуль не исправляет разрешения данных NPM.

[compose.example.yaml](compose.example.yaml) содержит полный пример для отдельного стенда с официальным NPM 2.16.0. Не запускайте его с новым пустым `./data` вместо данных работающей установки.

Если админка опубликована через ещё один reverse proxy, направьте его upstream на `cf-dns:8080` и проксируйте также `/__cf/`. Заголовок `Host` должен соответствовать origin браузера. CSP должна разрешать скрипты и CSS с того же origin: модуль не отключает CSP. Для передачи токена используйте защищённый административный канал (HTTPS/VPN).

## Cloudflare Token

Нужны права **Zone / DNS / Edit** и **Zone / Zone / Read**, ограниченные нужными зонами. При сохранении токен проверяется чтением списка активных зон. Поле пароля не возвращает сохранённое значение; пустое поле сохраняет текущий токен. Отдельная кнопка удаляет токен, оставляя DNS-записи.

Token хранится в AES-256-GCM в `state.json`; ключ — отдельный файл `key` в том же volume с правами 0600. Это защищает от случайной утечки содержимого state.json, но доступ ко всему volume позволяет расшифровать token. Резервируйте оба файла вместе. В frontend и ответах API token отсутствует. API модуля проверяет текущую сессию через `/api/users/me` и допускает только администраторов NPM.

## Внешний IP и ограничения DNS

Поддерживается публичный **IPv4 и A-записи**. Автоопределение использует `api4.ipify.org`, затем `ipv4.icanhazip.com`. Оно определяет адрес выхода **контейнера**: при VPN, policy routing или размещении на другом сервере это может отличаться от WAN домашнего пользователя. Настройте прямой выход worker или задайте публичный IPv4 в Settings. CGNAT, доступность портов и входящий маршрут модуль не исправляет.

При выборочной VPN-маршрутизации можно задать проверенные прямые HTTPS endpoints в `IP_DISCOVERY_URLS`, через запятую. Допускается ответ в виде IPv4 или JSON-строки. Например, `https://ifconfig.me/ip,https://ipv4-internet.yandex.net/api/v0/ip`. Эти адреса нужно проверить из контейнера и сравнить с WAN роутера. При их ошибке worker сохраняет DNS и не переключается на стандартные endpoints, которые могут выходить через VPN.

AAAA не меняются и не удаляются; при Sync ON наличие AAAA показывается предупреждением. CNAME/NS на том же имени и несколько A-записей приводят к ошибке вместо произвольной перезаписи. Единственная существующая A-запись становится управляемой при включении Sync, даже если была создана вручную. PATCH сохраняет посторонние метаданные; для proxied используется TTL Auto.

Если один домен есть в нескольких Proxy Hosts, конфликт разных желаемых Proxy блокирует синхронизацию. Удаление блокируется, пока этот домен синхронизирует другой хост. При смешанном Proxy у доменов одной строки отображается предупреждение; кнопка Proxy устанавливает общий режим.

## NPM с MariaDB/MySQL

SQLite — основной вариант. Для внешней базы можно использовать API NPM без прямого подключения к MariaDB. Создайте отдельную сервисную учётную запись NPM, имеющую просмотр **всех** Proxy Hosts, и передайте identity/пароль файлами Docker secrets. Для этой учётной записи API login должен работать без 2FA; обычные администраторы интерфейса могут использовать 2FA.

```yaml
services:
  cf-dns:
    environment:
      NPM_SOURCE: api
      NPM_URL: http://app:81
      NPM_IDENTITY_FILE: /run/secrets/npm_identity
      NPM_SECRET_FILE: /run/secrets/npm_secret
    secrets:
      - npm_identity
      - npm_secret
    volumes:
      - cf-dns-data:/data
secrets:
  npm_identity:
    file: ./secrets/npm_identity
  npm_secret:
    file: ./secrets/npm_secret
```

В этом режиме read-only mount данных NPM не нужен. API token сервисной учётной записи хранится только в памяти и автоматически обновляется входом по credentials. Файлы secrets исключены из Git.

## Обновление и отключение

Точки интеграции проверены по исходникам официального **NPM 2.16.0**: `/api/users/me`, `/api/nginx/proxy-hosts`, SQLite `proxy_host`, `localStorage.authentications`, `.domain-name` и меню внутри Settings card. Модуль не встраивает сборку frontend NPM и не требует повторного патча его файлов при обновлении образа.

Совместимость со всеми будущими версиями заранее не гарантируется: изменение этих контрактов потребует обновления `source.js` или `public/module.js`. Фоновая синхронизация не зависит от разметки UI. При неизвестной/неоднозначной строке адаптер не добавляет к ней кнопки, чтобы не менять чужой хост. Ошибка чтения source прекращает текущий цикл записи и показывается в настройках. Перед переходом на новый NPM проверьте на стенде: вход, Settings, таблицу/сортировку, хост с несколькими доменами и один полный цикл worker.

Для отключения остановите `cf-dns` и верните исходную публикацию административного порта NPM. DNS-записи сохранятся. Не удаляйте volume модуля, если нужно сохранить token и флаги для повторного подключения.

## Локальные проверки

```sh
npm run check
npm test
python3 -m unittest discover -s test -p '*_test.py' -v
npm run demo
# http://127.0.0.1:8088/nginx/proxy
```

`npm install` не нужен. Тесты проверяют worker, сохранение состояния, Cloudflare API-контракты на mock, read-only SQLite и HTTP gateway с настоящим локальным HTTP-сервером. `demo` использует изолированный HTML-стенд и DNS в памяти; не обращается к реальному NPM/Cloudflare. SQLite API в Node 24 может печатать ExperimentalWarning.

Изолированная проверка native-установщика на Linux с nginx/OpenRC:

```sh
docker build -f test/native/Dockerfile -t npm-cf-dns-native-test .
docker run --rm --init \
  --sysctl net.ipv4.ip_unprivileged_port_start=1024 \
  npm-cf-dns-native-test
```

Выполнены `npm run check`, 19 Node.js-тестов и 5 Python-проверок native installer. В браузере изолированного стенда проверены desktop render, мобильная ширина 390 px, горизонтальная прокрутка таблицы, Sync/Proxy, сортировка строк, подсказка и Escape, сохранение настроек, отмена/подтверждение удаления для хоста с двумя доменами, вкладки Settings и навигация стрелками.

Docker-вариант установлен и проверен рядом с официальным NPM 2.16.0: авторизация, worker, восстановление после restart, nginx config и сохранение реальных Cloudflare-записей проверены в целевой среде. Native-установщик проверен с реальным nginx/OpenRC в изолированной Linux-среде: установка, непривилегированный процесс с правом bind порта 81, gateway, SQLite, restart и отключение. Это не проверка нативной установки самого NPM на каждой поддерживаемой Linux-системе; systemd lifecycle отдельно не проверялся.
